기업용 교육 플랫폼의 개발·운영 중 확인한 문제의 원인과 수정, 확인 범위를 정리했습니다.

실무 사례

사례는 당시 코드·테스트 정의·저장된 실행 기록을 기준으로 작성했습니다. 회사 테스트를 현재 환경에서 다시 실행한 결과는 아닙니다.

직접 확인하지 못한 운영 결과와 한계는 각 사례에 표시했습니다. 회사 코드와 고객 정보는 공개하지 않습니다.

문제·수정·확인

근거 안내 · 실무 사례는 당시 코드·테스트 정의·저장된 실행 기록을 기준으로 작성했습니다. 회사 테스트를 현재 환경에서 다시 실행한 결과는 아닙니다. 운영 개선 수치와 실행 결과가 없는 항목은 각 사례에 표시했습니다.

이엠캐스트 · B2B 리테일 교육 플랫폼 · 백엔드 개발·운영

REST API와 관리자 기능을 개발하고 플랫폼 버전 전환, 배치·메시징 처리, 운영 오류 대응을 수행했습니다. 아래에서는 그중 문제의 원인과 수정 과정, 확인 범위를 설명합니다. 회사 코드와 고객 정보는 공개하지 않습니다.

저장 시점의 상태 재검증락 경합과 트랜잭션 경계배치 중복 제어와 누락 감지복합 식별자와 페이지 집계메시지 요청과 결과 처리

저장 시점의 상태 재검증

설정 화면을 연 뒤 관련 작업이 시작되면, 이전 상태를 기준으로 저장하면서 기존 데이터와 변경된 처리 기준이 달라질 수 있었습니다.

담당 범위
서버 재검증·변경 차단·후속 갱신 조건 수정과 회귀 테스트.
문제·원인
화면 진입 시점에만 확인한 상태를 저장 단계가 그대로 사용했습니다. 변경 적용 전의 서버 조회와 후속 데이터 갱신 조건을 함께 확인했습니다.
판단·수정
저장 직전 현재 이력을 다시 조회하고, 화면 진입 후 작업이 시작됐다면 변경을 차단했습니다. 입력된 이전 상태가 없으면 요청을 거절하고 후속 데이터 갱신도 같은 조회 기준으로 통일했습니다.
테스트·확인 내용
상태가 유지된 경우, 저장 전 상태가 바뀐 경우, 기존 이력이 있는 경우, 필수 입력이 누락된 경우를 단위 테스트로 확인했습니다.
테스트 범위
저장 전 상태를 다시 확인하는 수정입니다. 상태 조회와 저장 사이의 동시 변경까지 DB에서 원자적으로 차단하는 방식은 아닙니다.

락 경합과 트랜잭션 경계

동시 요청으로 주문을 저장하는 과정에서 DB 데드락이 발생했습니다. 결제 처리를 별도 트랜잭션으로 옮긴 뒤에는 앞 단계에서 아직 커밋하지 않은 요청 상태를 조회하지 못해 결제가 실패하는 문제도 드러났습니다.

담당 범위
주문 처리의 분산락 적용과 트랜잭션 범위 조정에 참여했습니다.
문제·원인
주문 저장·컬렉션 갱신의 락 경합과, 결제 요청 상태를 바꾸는 트랜잭션의 커밋 시점을 함께 확인했습니다. 별도 트랜잭션 도입만으로 호출 전체의 정합성이 보장되지는 않았습니다.
판단·수정
주문 단위 분산락과 별도 결제 트랜잭션을 적용했습니다. 결제 요청 상태를 먼저 커밋하도록 호출 경계를 조정하고, 락 관련 오류만 제한적으로 재시도했습니다. 복구 시 이미 결제된 주문은 완료 상태를 확인해 반환했습니다.
테스트·확인 내용
초기 QA에서 결제 요청 상태를 읽지 못하는 문제가 드러나 커밋 순서를 수정했습니다. 관련 테스트는 동시 요청·락 재시도·결제 완료 주문의 재처리를 다룹니다.
테스트 범위
최종 테스트 실행 결과와 운영 데드락 재발률은 확인하지 못했습니다.

배치 중복 제어와 누락 감지

Spring 스케줄러가 서버마다 실행되면서 동일 배치가 두 번 처리됐습니다. 수정 전에는 API 서버를 한 대로 제한해 임시 대응했습니다.

담당 범위
분산락 적용과 배치 모니터링을 담당했습니다. 실행 상태·처리 건수·실행 시간을 기록하고 어떤 고객사의 어떤 작업에 문제가 있는지 식별하도록 했습니다.
문제·원인
각 서버의 스케줄러가 별도로 실행돼 같은 배치를 중복 처리했습니다. 서버 간 공유 락이 필요했습니다.
판단·수정
ShedLock과 Redis 기반 락 공급자를 적용했습니다. 배치별 락 이름과 유지 시간을 설정했습니다. 이후 별도 개선으로 고객사·배치별 성공·실패·락 미획득·발행 누락·처리 결과 없음을 집계하고, 예정 시각 1시간 뒤 Slack 요약을 보내도록 구현했습니다.
테스트·확인 내용
서버 로그와 DB 기록으로 배치 실행 결과를 확인했습니다. 모니터링 코드에는 예정된 발행 횟수와 실제 기록을 비교하는 로직, 시간대별 집계와 관련 테스트가 있습니다.
테스트 범위
락 유지 시간을 넘긴 작업과 장애 복구 중의 중복 실행까지 보장하지 않습니다. 전후 중복 횟수는 당시 로그 원본이 없어 수치로 제시하지 않습니다.

요청 발행 누락과 발행 후 결과 미수신을 구분했습니다. Slack 요약에는 정상 처리 결과도 포함했습니다.

복합 식별자와 페이지 집계

같은 사용자에게 여러 그룹 데이터가 있는데 사용자 ID만으로 구분해, 선택한 삭제 항목 일부가 누락됐습니다. 조회 제외 조건과 페이지 합계도 실제 행 수와 어긋났습니다.

담당 범위
복합 필터 모델, 서버 조회·삭제와 동등성 수정, 페이지 경계·다중 그룹 테스트.
문제·원인
사용자 ID만 비교하는 컬렉션 동등성이 다른 그룹을 같은 항목으로 취급했습니다. DB 조회 후의 필터링과 근사 합계가 페이지 경계에서 또 다른 불일치를 만들었습니다.
판단·수정
사용자 ID와 그룹 유형을 조합한 식별자를 조회·삭제·동등성에 적용했습니다. 제외 조건을 QueryDSL WHERE 절로 옮겨 조회와 집계 기준을 맞췄습니다. 많은 제외 항목은 POST 본문으로 전달하고 기존 단일 유형 조회는 유지했습니다.
테스트·확인 내용
같은 사용자의 서로 다른 그룹이 Set에 남는지, 선택한 조합만 삭제되는지, 그룹 제외 조건과 페이지 총건수가 맞는지 테스트했습니다.
테스트 범위
중복 요청 제한의 추가 통합 테스트와 운영 성능 측정은 포함하지 않았습니다.

메시지 요청과 결과 처리

대량 발송이 동기 RPC의 응답 제한을 넘으면서 실제 수신과 관리자 화면의 실패 이력이 어긋났습니다. 발송 요청 접수와 최종 결과를 구분해야 했습니다.

담당 범위
메시징 타임아웃 대응에서 동기 응답 대기를 없애고 요청 접수와 결과 처리를 분리하는 작업에 참여했습니다.
문제·원인
기존 발송 호출은 RPC 응답을 5초간 기다리고, 그 안에 응답이 없으면 실패로 기록했습니다. 대량 발송이 이 시간을 넘으면 실제 수신과 실패 이력이 어긋났습니다.
판단·수정
발송 요청을 RabbitMQ 큐에 비동기로 보내고 대량 요청은 HTTP 202로 접수 응답을 반환하도록 바꿨습니다. 별도 결과 큐 리스너가 최종 이력 갱신 큐로 전달하며, 처리 예외는 제한 재시도 후 DLQ로 분리합니다.
테스트·확인 내용
변경 코드와 업무 완료 기록에서 RPC 호출 제거, 비동기 발행, HTTP 202 응답, 결과 리스너와 재시도·DLQ 설정을 확인했습니다.
테스트 범위
HTTP 202는 요청 접수만 뜻합니다. 채널별 최종 발송·DB 저장, 중복 처리 방지와 DLQ 재처리의 실행 결과는 확인하지 못했습니다.
